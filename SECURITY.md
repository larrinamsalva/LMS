# Security policy and current boundaries

Version 0.1 is an experimental fictional-data demo. Do not use it for real businesses until the [roadmap acceptance gates](ROADMAP.md) are satisfied. Report a suspected vulnerability privately through GitHub Security Advisories if enabled for this repository; otherwise contact the maintainer privately. Do not post secrets or personal data in public issues. No support-response SLA is offered.

## Host-only native readiness

The [native readiness coordinator](docs/native-upgrade-readiness.md) is restricted to privately attested fictional test databases on one literal loopback PostgreSQL 16 endpoint. Exact instance/organization allowlists, approved actual maintenance superuser/ownership, server/destination identity, offline/migration leases, source table fences, private files, empty targets and strict original migration/version checks fail closed. It performs no source DML/DDL or schema transformation and never clears an activation marker. Existing native backup/restore remains the sole archive implementation; no arbitrary archive, public route, hook input or report-as-approval path is exposed.

Success requires scoped retained-data/catalog comparisons, transient-state purge, continued refusal by both runtime lease paths, unchanged source evidence and completed archive cleanup. Partial/failing/interrupted/unclean operations never report verified readiness. Reports exclude rows, IDs, hashes, credentials, raw errors and commands. Fictional provenance and physical locality depend on trusted host/operator/server custody; allowlist names and email spelling cannot classify data or resist administrator compromise. External lineage/latest-checkpoint acceptance, recovery identity/approval, production acceptance, real-data handling and power-loss/disaster recovery remain unverified. Public Studio backup statuses are unchanged; restored databases remain blocked.

## Verified design boundaries

- Every business table enables and forces PostgreSQL RLS. The ordinary `lms_app` role is not the owner, superuser or a BYPASSRLS role. Direct database tests cover organization isolation, insert/update rejection, scope reassignment, viewer/staff permissions and append-only history.
- Membership rows, not UI choices or user-editable profile metadata, authorize access. Membership/user/organization provisioning is trusted host code only. The demo issues a random opaque 256-bit HttpOnly, SameSite=Strict cookie, scoped to its server-created fictional organizations; HTTPS gets Secure cookies.
- Each service transaction sets a validated identity locally, switches to `lms_app`, checks role and uses parameterized SQL. End users must never receive raw SQL access or host credentials. `lms.user_id` is a trusted-server assertion, not a client authentication mechanism; a future identity adapter must verify the user before constructing a Principal.
- All demo HTTP mutations check origin and strict allowlisted input. Request size is measured on streamed bytes (64 KiB for demo), with content-type and UTF-8 checks. Module/entity/field keys and values are validated; no eval, raw HTML rendering, dynamic SQL identifiers or uploaded executable modules.
- Request-scoped script CSP nonces protect the page. Development allows unsafe-eval for Next.js debugging; production does not. Inline styles remain allowed for framework compatibility. No third-party scripts, analytics or remote fonts are loaded.
- Ordinary sessions cannot delete records or alter/delete audit/config history. Record identity is immutable. Migration 1 has a narrow private SECURITY DEFINER audit trigger with empty search_path and revoked public execution; it snapshots the just-authorized row. Migration 3 adds three independently authorized owner-access commands; migration 4 adds a private credential-audit trigger. All use fixed empty search paths and revoked public execution. Audit access is owner/admin only.
- Configuration changes and record edits serialize on an organization lock; expected revisions reject stale writes. Disabling a module preserves rows. Populated schemas cannot be destructively changed by the configuration API.
- Finance, live invoices, messaging, AI and payment routes/providers are absent. Generic JSON records are not financial ledgers. New external/sensitive actions need a reviewed permission + explicit confirmation transaction; hiding controls or a browser checkbox is insufficient.

## Known limits / acceptance gates

The demo database and sessions are process memory. Restart clears them; expiry removes access and later demo starts prune expired data. There is no real web authentication, persistent business endpoint, disaster-recovery guarantee, document object store, virus scanning, brute-force protection, per-IP rate limit, multi-process demo coordination or public service availability guarantee. A separate experimental host-only PostgreSQL adapter provides durable storage; it is never selected by the public demo. A global cap bounds session/record/revision growth; it is not a complete denial-of-service defense. Do not expose the runtime’s database API directly or use a serverless/horizontal deployment as-is.

No role should have access to another organization's rows, even with a forged organization ID. Staff in this first slice can access all operational records in their organization; per-crew/per-property assignment permissions are deferred. Field-level secrecy and complex record relationships are not supplied by custom JSON. Backups need identity/secrets, configuration, database and object bytes plus a tested restore; workspace JSON alone is not a backup or import format guarantee.

PGlite executes real PostgreSQL policies but does not test network PostgreSQL concurrency, Supabase Auth/PostgREST/Storage, hosted settings or production deployment. Source installs keep dependency licenses; redistribution of bundled platform binaries requires a separate LGPL/source/relinking review. No deployment or security certification is claimed.

## Experimental PostgreSQL storage

The runtime adapter refuses administrator/schema-owner/database-owner credentials, elevated attributes, INHERIT logins and unexpected role memberships. Pools are bounded and transactions retain one checked-out connection. Identity is trusted host input; RLS does not authenticate a caller. Arbitrary SQL/database credentials must never reach a browser, and no persistent-business endpoint is enabled in this phase. The existing engine limits (250 records/40 config revisions) still apply to this experimental adapter.

Migration/initialization commands require an explicitly named local fictional database and separate administrator credentials. Migration history is checksum-checked and transactional. Unknown/untracked schemas are not silently adopted. Native backup/restore commands use private new files, refuse populated restore targets and restore in one transaction; only trusted archives may be used. Full production recovery still needs tested cluster-role/credential recovery, identity revocation, encryption/retention/off-device copies, future object storage and operational procedures. Remote TLS hosting, failover, database server crashes and committed-but-unacknowledged writes remain unverified. Record saves/archives with operation UUIDs now have the scoped receipt contract below; unkeyed/configuration writes still require inspection after an uncertain commit and must not be automatically retried. Owner access confirmations have their own durable receipt contract below.

Network tests use disposable, fictional PostgreSQL databases in CI. Local public-demo checks do not establish persistent backend acceptance. See [the separate evidence record](docs/postgres-verification.md). No production connection, deployment or real-business authorization is implied.

## Local identity foundation

The new identity host is not mounted in Next.js and cannot enable itself from environment variables. Provisioning is trusted maintenance for @example.test identities; it grants no business membership. Better Auth handles hashing/cookie signing; session caches and sliding renewal are disabled. The unmounted wrapper exposes a strict allowlist, exact origins, bounded JSON, token-free JSON and distinct HttpOnly/SameSite cookies. A shared database-backed local sign-in limit ignores caller forwarding headers; public proxy/per-account/rate-limit design is still a gate.

Identity service credentials have a private schema and cannot read business records; business credentials cannot read identity records. Session tokens in that database and password hashes are credential-sensitive. Native backups exclude session/verification data; guarded restores purge it before success. Offline restore and re-authentication are required. Do not revive old sessions by attaching a host to a raw/manual restored archive.

Fresh validation rejects later requests after expiry/revocation. Migration 3 fences owner access commands against session deletion; ordinary record/config operations still lack that fence. No verified mailbox ownership, recovery/MFA, membership UI, public login, HTTP deployment or complete disaster recovery is claimed. See the [identity contract](docs/local-auth.md) and [verification evidence](docs/local-auth-verification.md) before any integration.

## Owner access commands

The [host-only access service](docs/owner-access.md) requires a fresh identity/session from a sign-in within five minutes, owner role, stored five-minute review and explicit confirmation. PostgreSQL rechecks the matching live session and owner after acquiring organization locks. Application roles cannot write memberships directly. Three private definer commands use fixed empty search paths; only their narrow entry points are executable by lms_app. Internal helpers and private review/bootstrap tables remain inaccessible. A roster can be read only by its organization owner. Confirmed changes retain reasons and before/after roles in append-only audit history; no session tokens or internal session UUIDs are returned.

Ordinary changes cannot remove/demote the owner. Dedicated handover atomically makes an existing eligible member the sole owner and the previous owner an admin. Pending reviews are session-bound, expire, reject stale revisions and are removed on session deletion. Confirmation receipts make retries safe for these commands only. Revocation waits behind an already authorized in-flight access command; it does not reverse it. Backups exclude pending approvals; restoring clears sessions and pending approvals. Re-authentication and a new review are required.

The local bootstrap command requires separate administrator credentials, a provisioned fictional identity and explicit confirmation. It creates a new workspace, cannot adopt an existing one and cannot reverse a later handover on retry. Real-user onboarding, password recovery, recent-authentication/MFA, public transport and full recovery remain incomplete. See [verification evidence](docs/owner-access-verification.md).

## Credential lifecycle

The [password-change host API](docs/account-lifecycle.md) reuses Better Auth's cookie/session validation, password verification and configured hashing. Strict confirmed input has no target identity, role or session fields. A compare-and-swap credential lock and the same recent-session helper used by owner commands prevent stale credential overwrites and expired/revoked-session writes. Password update, revocation of every subject session/pending approval and the credential event commit together. Failed audits/reused operation IDs roll everything back. Sign in again after success; no new session/token is issued.

Supported sign-in holds a credential SHARE lock across verification/session creation. A separate bounded coordinator pool prevents lock waiters starving identity queries. A shared atomic per-account password-attempt limit counts incorrect credentials. Raw identity-service/database credentials remain trusted and powerful, never browser input. Private credential events contain no secrets/session IDs; app access and direct service-role mutation are denied. Existing business history/roles are untouched.

No public password reset/deletion/admin takeover or recovery endpoint is exposed. A separately guarded offline reset is described below. The [offline recovery design](docs/local-recovery-plan.md) is implemented only through the blocked offline contract below; unverified email is never sufficient. An older backup can restore an older password and operation history even though sessions are purged. Keep recovery offline until credential rollback, signing-key/role recovery and identity verification are accepted. Password changes and recent authentication are not MFA, complete account recovery or authorization to enable persistent business routes.

## Controlled offline recovery and activation blocker

[Offline recovery](docs/offline-recovery.md) requires the separate local administrator, no attached runtime hosts, a private pre-enrolled trust registry and two independent Ed25519 signatures. Registry enrollment has a server-recorded 24-hour cooling-off period; an unverified email, new claimant-supplied record or claimed business role is never sufficient. Unique people/keys and subject separation are checked in software; physical identity evidence and independent human key custody remain trusted enrollment responsibilities. No public reset route exists.

Cases bind subject/database/credential/membership/evidence/registry versions and expiry. Verification and approval have separate signed purposes. The same credential mutation helper and maintained Better Auth codec handle replacement; subject sessions/pending approvals, password/version and credential/recovery audits commit together. Business roles/history are preserved. Failed final writes roll back; a one-use case cannot replay. Ordinary runtime roles cannot read/mutate recovery tables or credential versions.

Auth/persistent hosts hold lifetime shared maintenance leases. Recovery/restore take exclusive locks; busy hosts/transactions cause refusal. Database mutation guards also enforce the online gate. Opening recovery and completing it keep activation blocked. Native restores purge recovery cases and install a marker even for archives predating the schema; migration/init cannot clear it. Both normal factories refuse blocked attachment. There is **no activation override**. Trusted offline password verification creates no session.

An older archive may contain an older password hash and lose later credential history. This PR enforces a deployment blocker rather than claiming full rollback resistance. The external lineage foundation below does not complete key/role recovery or end-to-end activation review. A superuser/manual restore can bypass database markers and is outside this protection; never attach such a database. No real-user identity verification, public recovery, production activation or complete disaster recovery is certified.


## Independent lineage, no activation

The [lineage foundation](docs/credential-lineage.md) records metadata-only credential/recovery changes in the source transaction. Offline proposals and read-only assessment reuse existing maintenance locks, prior registry enrollment, file validation and operator-signature infrastructure. External two-person checkpoints commit the complete event/version history and opaque keyed credential-state commitments. Normal runtime roles receive no lineage grants; signing private keys never enter the utility. Checkpoints require a separately protected latest digest supplied by independent custodians; an old valid signature chain is insufficient.

The protected key and highest acknowledged receipt must remain outside database/backup/runtime custody. Files stored alongside the database do not meet this assumption. Lost, stale, corrupt, substituted or conflicting evidence, unsupported key/root rotation, mismatched state, residual sessions/approvals and unsupported restore histories fail closed. Initial baseline adoption attests current state, not the truth of pre-enrollment history. External publication is manual and not atomic with online changes; an unwitnessed tail is refused. This is tamper evidence relative to independent trust, not protection against a malicious database server/verifier or combined administrator/custodian compromise. No durable monotonic witness or production key-custody system is supplied.

A successful assessment changes no database rows and always reports activation disallowed. It does not verify a person's identity, approve sole-owner recovery, prove password knowledge, revoke residual state or authorize reattachment. All existing blockers remain. Identity-specific acceptance, independent durable freshness, key/role recovery and post-acceptance authentication/access checks must precede any future activation implementation. There is no force-unblock option or public lineage/recovery/auth endpoint. See [verification and remaining limitations](docs/credential-lineage-verification.md).


## Checkpoint publication custody

The [publication utility](docs/checkpoint-publication.md) is a separate offline custodian boundary with no PostgreSQL connection, HMAC key or private signer. Existing Ed25519 checkpoints plus two purpose-specific publication signatures bind the immutable journal, exact parent receipt, store/stream/registry, generation, unique request and expiring approval. Private Linux storage and a kernel advisory lock serialize writes; file/directory sync precedes success. Pending/incomplete, stale, missing, conflicting or unsupported history refuses verification without choosing an older head. Exact unexpired intents can resume; expired/corrupt intents remain blocked with no clear/force path.

The root and highest approved/acknowledged receipt must be retained independently of both database and publisher snapshots. Ordinary DB administrators must not control that custody account/device. This is a deployment responsibility, not something POSIX mode bits prove. An independently retained receipt detects a lost/rolled-back store prefix; rollback of every root/receipt/store/key together remains undetectable. No monotonic hardware/remote witness, real-person identity verification, physical power-loss certification, compromised-server defense or production custody acceptance is claimed. Source and DB transactions are not atomically published. Instance transitions, rotation, expired-intent repair and complete recovery acceptance are deferred. All activation blockers and public-demo boundaries are unchanged.


## Shared relationships and scheduling

Empty-search-path definer triggers have revoked public execution and touch only scoped derivatives of the authorized source. A per-organization coordination row serializes relationship/archive checks and rejects stale repeatable-read mutation attempts. Existing runtime activation write guards still execute; scheduling creates no alternate persistent/authentication endpoint.

This is database-contained idempotency, not external rollback protection: an older backup can lose later business operations, and every restored database stays activation-blocked. Ordinary business writes still lack complete production session fencing. Resources are fictional operational catalog records, not authenticated staff accounts or crew assignment authorization. All prior credential/recovery/publication gates and administrator-compromise limits remain.


## Employee crews and availability
