# Equipment & Tools — fictional registry and custody

Equipment is an optional shared module, disabled in existing organizations, saved BuildPlans and reviewed Gallery starters. It tracks individual reusable machines/tools. Consumable quantities and movements stay exclusively in the existing inventory ledger. No GPS, payroll, customer messages, purchasing, depreciation, accounting or payment operation is added.

## Try it

1. Run the existing `npm ci` / `npm run dev` setup and open the fictional no-login demo. In Studio, explicitly choose **Equipment & Tools**. Its dependencies are Inventory, Workforce and Tasks; Workforce also requires Scheduling and Customers. Save and use the existing impact review and publication confirmation. A separate real Engine preview is also supported within existing quotas.
2. In **Equipment & Tools**, add a machine, permanent business equipment ID and an existing storage location. Add optional category/description, manufacturer/model, serial, barcode/tag, purchase date, USD purchase-cost metadata and notes. Empty purchase cost is supported and is explicitly non-accounting.
3. New items start **Needs inspection**. An owner/admin selects **Review release**, an active inspector, date, notes and explicit confirmation. Only then can it become Available.
4. **Check out** to a named active employee. Optionally choose their effective Crew/Worker resource and a current job/task. Review checkout and expected-return times in the business time zone and confirm. A crew does not replace the responsible named employee. Select **Begin use** to record use; no employee calendar or payroll is altered.
5. **Record return** with actual time, observed condition, notes and confirmation. Returning a serviceable item does not clear an unresolved problem. The authorized recording operator and responsible employee remain traceable.
6. **Report problem** to mark Needs inspection or Out of service. Custody remains with the employee; an In use flag becomes Checked out. An owner/admin links an existing open Task through **Open maintenance**, then **Record service**, then separately **Review release**. Service completion alone leaves it Under maintenance. Release review retains the recorded next inspection date unless deliberately changed. Create work in the existing Tasks area; no duplicate tasks are generated.
7. **Retire equipment** requires an owner/admin, an explicit terminal confirmation, notes and no active checkout. The permanent ID, metadata revisions, completed assignments and all history remain retained. Retirement cannot be undone in this phase or used to free an identifier.

Search names, business IDs, categories, serials and barcode/tag text. Filter physical/custody status, home storage location and active responsible employee. Cards show current custody, return deadlines, inspection indicators and expandable metadata/timelines. Serial numbers are not assumed globally unique. Permanent business IDs and current nonempty barcode/tag values are case-insensitively unique within each organization. Business IDs cannot be reassigned; barcodes may be updated through an audited metadata revision.

## Condition, custody and dates

Physical condition is Serviceable, Needs inspection, Under maintenance, Out of service or Retired. Custody is independently Checked out, In use or Returned. A machine with an unresolved repair never appears available merely because it was returned. Problem reports require a maintenance task and completed service before release; a new-item inspection can be reviewed directly. Only one active checkout is permitted per item.

Times use existing explicit-offset/Temporal validation and whole-minute precision within 2020–2100. The UI reuses business-zone conversion, rejects DST gaps and requires a first/second choice for repeated wall times. Expected return must follow checkout within 366 days; actual return cannot predate checkout. New checkouts cannot overlap retained actual returns or predate the last service/inspection calendar date. Service/release dates cannot move backwards; optional next inspection must follow the recorded service date.

Overdue and upcoming/due inspection indicators are calculated from dates on the client and refreshed on screen. They do not execute jobs, send notifications, change a condition or claim safety certification. This is not a future equipment reservation/calendar-allocation system. Existing Scheduling Equipment resources remain compatible and independent; an explicit reviewed mapping/reservation design is a later phase. Custody does not assert employee working hours, qualifications or physical location. Effective crew membership is validated/snapshotted at checkout; future membership expiry does not transfer custody.

## Engine, permissions and immutable history

Metadata uses the existing generated RecordForm, `Engine.saveRecord`, validators, roles and operation receipts. Owner/admin writes require an operation ID. The `equipment` 1.0.0 manifest and locked entity definition are reviewed optional extensions to the existing BusinessConfig/BuildPlan 1/2 readers. No old starter, Gallery digest, JSON/ZIP envelope, logo protocol or publisher attestation changes. Populated-schema restrictions and explicit configuration publication/rollback remain authoritative. Module disabling hides the area while retaining data, links, history and authorized exports/backups.

`Engine.writeEquipment(principal, organizationId, command, operationId)` accepts only the reviewed checkout, begin-use, return, report-problem, open-maintenance, record-service, release and retire vocabulary. Trusted host code must resolve identity first; never accept a caller-provided user ID in a persistent transport. Current owners/admins/staff may check out, record use/return and report blocking problems. Only owners/admins edit metadata, record/release maintenance or retire. Current authority is rechecked even for an exact committed retry of a sensitive action. Employee profiles are descriptive records, not authentication identities or permission grants.

Every action binds current configuration/equipment revisions; return/use also pin the exact checkout ID/revision. Related employee/crew/work records must be active, enabled, same-organization and at the reviewed revision. Crew selection additionally requires effective membership at checkout. Active equipment prevents incompatible employee deactivation, relationship archiving or membership changes. History retains UUID references and necessary equipment notes, not copied contact details, account secrets or GPS information.

Additive migration **017_equipment_lifecycle** introduces forced-RLS `equipment_state`, `equipment_checkouts` and append-only `equipment_events`, with scoped foreign keys and a partial unique active-checkout index. Events retain every registry/action revision, state, applicable checkout snapshot, actor, operation and server time. Completed checkout projections cannot be updated/deleted. App roles have SELECT only on these tables; reviewed triggers/functions own mutations. Metadata and lifecycle commands share the original records, organization lock, record epoch, audit and operation-receipt infrastructure. Guards independently validate raw writes; there is no second business engine.

The organization lock and epoch fence serialize checkout, return, metadata, configuration and relevant employee/crew changes, including stale repeatable-read snapshots. Exact committed retries by the same currently authorized actor return historical evidence; conflicting requests or stale state refuse. Receipts, records, state, checkouts, events and audits commit atomically. Ambiguous responses require retrying the same validated request and operation ID. No archive/delete action resets capacity or erases conflicts.

## Persistence, expiry and remaining gates

Apply migration 17 explicitly using [the stopped-host maintenance setup](postgres-setup.md). Earlier migrations/checksums are unchanged. New native tables join the closed backup/readiness inventory, so older evidence must be refreshed. Native tests must verify reconnection, exact same-schema dump/restore into a separate fictional quarantined database, unchanged source, scoped access and continued activation refusal. A restored backup is never authority to activate a database.

Persistent operations remain **host-only fictional PostgreSQL**. The only HTTP action is in the existing cookie/origin/scoped temporary demo. No persistent public equipment route or real-user acceptance is supplied. Due indicators and actor/date entries are not independent proof of physical custody, safety inspection, qualifications, production identity or financial compliance. Trusted host/database-administrator compromise and rollback of every backup remain outside these history guarantees.

Demo access still expires after two hours. Protected equipment/invoice histories cannot be safely deleted through ordinary expired-session cleanup; their expired sessions and SQL rows retain a bounded slot until the temporary server restarts. Their logo custody is dropped, cookies refuse access, and new sessions receive new identities/organizations. Up to 24 retained/active sessions per runtime remain the cap. Legacy sessions without protected ledgers retain existing cleanup. This conservative refusal preserves history rather than deleting it to regain capacity; a separate reviewed disposal design is needed for more flexible cleanup. It never purges persistent organizations.

Deferred: real-business transport/security/retention acceptance, image/camera barcode scanning, reservation-linked checkout and multiple-resource appointments, recurring maintenance, qualifications/safety certification, depreciation and purchasing.
